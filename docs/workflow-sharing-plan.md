# Workflow 流程模板分享实施方案

> 日期：2026-09-10
>
> 状态：设计方案，待实施。本文不表示相关接口、数据表或界面已经上线。
>
> 范围：在现有 Workflow 模块中增加面向内部成员的流程模板分享，支持图片与视频流程。

## 1. 目标与已确认决策

用户在流程库选择一个流程，将其已保存版本分享给指定内部成员。接收者获得一个属于自己的、可独立编辑和运行的流程副本。

| 项目 | 确定行为 |
| --- | --- |
| 分享对象 | 流程定义模板，不是某次运行 |
| 接收对象 | 门户内符合现有成员选择规则的有效成员 |
| 保留内容 | 节点、连线、端口、提示词、模型参数、布局和输出槽位 |
| 清除内容 | 输入图片／视频、所有生成结果、媒体地址、缓存引用和运行数据 |
| 接收后状态 | 图片／视频输入为空，输出槽位等待运行；文本提示词保留 |
| 流程名称 | 保持源流程原名，不追加“来自某某” |
| 来源展示 | 独立显示“来自：张三”，重命名不影响来源记录 |
| 数据独立性 | 双方后续编辑、运行、重命名和删除互不影响 |
| 重复请求 | 同一源流程、版本、发送者、接收者只产生一次分享副本 |
| 副本删除 | 分享记录长期保留；重复请求不会自动恢复已删除副本 |
| 执行行为 | 分享不创建生成任务，不调用供应商，不产生生成费用 |

本方案作为[现有 Workflow 实施方案](workflow-implementation-plan.md)的后续扩展，补充其首期未包含的跨用户分享能力。以本文为准的补充决策包括：新增 `workflow_shares`、服务端清理 Definition JSON、来源独立展示，以及删除副本后的历史记录语义。

本次不增加公开分享链接、实时协作、发送者素材访问授权、自动同步更新、条件判断、循环、分享通知服务或管理后台分享审计页面。

## 2. 当前实现与可复用能力

普通 Canvas 已有“选择成员 → 分享 → 接收者获得副本”的业务流程，但其媒体复制和名称处理不适用于流程模板分享。

| 当前模块 | 可复用部分 | Workflow 的处理差异 |
| --- | --- | --- |
| Canvas 分享弹窗 | 成员搜索、分页、多选、数量限制、提交状态与逐人结果反馈 | 改用流程模板说明及 Workflow 分享接口 |
| 门户成员查询 | 有效成员查询、排除本人、UID 校验 | 作为两类分享共同的成员能力 |
| Canvas 卡片操作区 | 分享图标、轻量按钮、事件隔离 | 在流程卡片增加同风格入口 |
| Canvas 分享服务 | 权限、版本检查、逐接收者处理的组织方式 | 不复制媒体、不拼接来源名称，不照搬媒体复制超时 |
| Workflow 定义校验 | 图结构、类型、端口、连线、输出槽位及大小限制 | 清理后再次校验，允许待补充素材的模板 |
| Workflow 创建与仓储 | 新 ID、接收者归属、版本初始化、事务模式 | 副本与分享记录必须在同一事务内提交 |
| Workflow 列表与编辑器 | 卡片、节点渲染、独立保存与运行 | 增加来源展示，空媒体仍使用现有占位状态 |

当前 `CopyWorkflow` 用于本人复制流程，会保留图中的媒体引用，不能直接作为跨用户分享实现。当前运行快照、任务状态和结果记录与 Workflow 定义分离，分享不得从这些运行对象组装副本。

复用边界：抽取确有共同用途的成员选择能力和必要 UI，Canvas 与 Workflow 保留各自的分享业务服务、请求和说明文案；不建设通用分享引擎。

## 3. 用户操作流程

### 3.1 发送者

1. 在流程库卡片操作区点击分享图标；点击图标不触发打开流程。
2. 弹窗显示流程名称和本次分享的已保存版本。
3. 明确提示：“分享流程结构、模型参数和提示词，不包含输入图片、输入视频及生成结果。”
4. 搜索并选择接收成员，沿用每页 20 人、单次最多 50 人的规则。
5. 提交期间禁用重复点击，按接收者展示结果。
6. 部分成员失败时保留已成功结果，允许重试失败成员；网络结果不确定时可使用原版本重复请求。

首期入口设在流程库卡片，不新增编辑器顶部常驻分享按钮。编辑器返回流程库时沿用现有保存后离开逻辑；保存失败按现有方式提示，不绕过保存检查。

接口只分享服务端已保存的定义。请求携带用户看到的 `revision`；若版本不符，提示刷新并重新确认，不自动改为分享用户尚未确认的新版本。

流程正在运行、运行失败或从未运行，不影响模板分享。已保存源流程中的输入媒体即使失效，也不应因这些将被清除的引用阻止分享。

### 3.2 接收者

- 刷新或重新进入流程库后看到新副本，流程名称与源流程相同。
- 卡片用次要文字显示“来自：张三”，与现有更新时间等辅助信息保持一致。
- 打开后保留完整框架：文本提示词、生成配置和连线均可继续编辑。
- 图片／视频输入显示现有空输入状态；输出槽位显示现有“等待运行结果”。
- 用户补充素材后自行运行，沿用当前模型可用性、权限、参数和输入完整性校验。

分享不会授予接收者额外的模型权限。模型不存在、停用或不可用时提示接收者重新选择，不在分享过程中静默替换模型或改变参数。

### 3.3 分享结果与副本状态

| 场景 | 页面反馈 | 行为 |
| --- | --- | --- |
| 首次成功 | 已分享 | 接收者获得独立副本 |
| 同版本重复分享，副本存在 | 此前已分享，副本仍存在 | 返回原副本标识，不覆盖接收者修改 |
| 同版本重复分享，副本已删除 | 此前已分享，副本已删除 | 保留历史事实，不创建新副本，不显示打开入口 |
| 源流程新版本再次分享 | 已分享 | 按新版本创建新的独立副本 |
| 单个接收者失败 | 显示对应原因 | 不留下该接收者的半成品副本或成功记录 |

发送者不能因为持有副本 ID 就打开接收者的私有流程。所有打开入口仍须满足当前用户归属和对象存在性检查。

## 4. 分享内容与 Definition 清理

### 4.1 字段保留规则

以下使用当前 Workflow JSON 的实际字段名；讨论中的 `nodeId`、`slotId` 分别对应节点和输出槽位对象内的 `id`。

| 层级 | 保留字段或内容 |
| --- | --- |
| Workflow | `name`；另生成新的 Workflow ID 和接收者归属 |
| Graph | `version`、`nodes`、`connections` |
| 节点公共字段 | `id`、`type`、`position`、`width`、`height` |
| 文本输入 | `text`，保留用户提示词原意和内容 |
| 生成节点 | `inputPorts`、合法 `config`、`outputs` |
| 输入端口 | `id`、`type` |
| 输出槽位 | `id`、`type`、`position`、`width`、`height` |
| 连线 | `sourceNodeId`、`sourceSlotId`、`targetNodeId`、`targetPortId`、`order` |
| 生成配置 | 当前支持的 `providerId`、`size`、`resolution`、`quality`、`outputFormat`、`background`、`seconds`、`generateAudio` 及合法扩展参数 |

图内节点和槽位 ID 可保留，因为它们在具体 Workflow／运行范围内使用。只更换顶层 Workflow ID，不重建图内 ID，避免破坏上下游关系。

输出数量继续由输出槽位及现有配置规则表达，不新增第二套数量字段。沿用当前生成节点最多 9 个输入、9 个输出及具体供应商的限制。

### 4.2 必须清除或排除的内容

- 图片和视频输入节点中的 `mediaId`。
- `storageKey`、`url`、`signedUrl`、`localUrl`、`thumbnail` 及同类媒体展示地址、Blob URL、缓存键。
- 生成结果的媒体引用、预览地址、任务 ID、上游任务 ID、执行状态和错误信息。
- 所有运行快照、步骤执行、输出执行及重试记录。
- 供应商凭据、Token、密钥或其他不属于浏览器安全生成参数的内容。
- 发送者的 `workflow_media_refs` 和任何媒体持有关系。

当前节点类型定义中的持久媒体入口主要是 `mediaId`。上述其他地址字段用于明确分享安全边界，不表示它们都是当前合法的节点字段；以后扩展字段时也必须受同一规则约束。

### 4.3 服务端清理函数

增加 `sanitizeWorkflowDefinitionForShare()`，采用“按当前类型允许的字段重新构造”的方式，不能仅对原 JSON 删除几个字段后原样透传。

处理顺序：

1. 从拥有者范围内读取已保存源定义，固定本次源版本快照。
2. 依据节点类型重新构造 Graph，保留允许字段，清空全部媒体引用。
3. 深复制端口、输出槽位、连线、配置及扩展参数，避免清理过程修改发送者对象。
4. 扩展 `options` 只保留当前支持且经过参数校验的配置。检查嵌套字段，不允许媒体引用、地址或凭据通过扩展对象重新进入副本；无法判定为合法生成参数时返回明确错误，不随意改变生成语义。
5. 使用现有 Workflow 图结构、参数及大小校验重新校验清理结果。
6. 使用媒体引用收集逻辑再次检查，确保目标 Graph 不含任何媒体 ID，目标定义不产生媒体引用行。
7. 将清理后的模板交给分享事务写入。

提示词是用户明确要求保留的内容，不通过字符串替换扫描提示词并删除其中的 URL 或文字。媒体清理针对结构化资源字段，不改变文本语义。

模板允许图片／视频输入留空，因此不在分享阶段执行“必须具备所有输入素材”的运行前检查。接收者实际运行时再检查。

## 5. 数据模型与来源追踪

### 5.1 新增 `workflow_shares`

| 字段 | 逻辑类型与约束 | 含义 |
| --- | --- | --- |
| `source_workflow_id` | 字符串，非空，沿用 Workflow ID 长度约束 | 被分享的源流程 ID |
| `source_version` | 正整数，非空 | 源 Workflow 的 `revision` |
| `sender_uid` | 字符串，非空，沿用用户 UID 长度约束 | 发送者 UID |
| `recipient_uid` | 字符串，非空，沿用用户 UID 长度约束 | 接收者 UID |
| `created_workflow_id` | 字符串，非空 | 本次成功创建副本的历史 ID |
| `created_at` | 非空 UTC 时间，沿用项目时间序列化约定 | 本次分享成功创建时间 |

以以下组合建立唯一约束，可直接作为复合主键，不额外引入无用途的分享序号：

```text
source_workflow_id + source_version + sender_uid + recipient_uid
```

增加来源查询索引：

```text
recipient_uid + created_workflow_id
```

版本含义必须区分：

- `source_version`：源 Workflow 保存版本，对应 API 的 `revision`。
- `graph.version`：Graph 数据格式版本，不参与分享幂等。
- 副本 `revision`：按新建 Workflow 初始化，从自身版本开始，不沿用源保存版本。

不在该表保存完整 Graph、图片、视频或签名地址。表用于分享幂等和来源，不替代 Workflow 定义或运行表。

### 5.2 删除策略与历史语义

`workflow_shares` 表达的是“这次分享曾经成功发生”，不是“这个副本现在仍可访问”。

- 接收者删除副本：保留分享记录及原 `created_workflow_id`。
- 发送者删除源流程：保留接收者副本及分享记录。
- 删除流程不能被分享记录阻止，也不能级联删除分享记录。
- `source_workflow_id` 和 `created_workflow_id` 作为历史标识保存，不建立要求对应存活 Workflow 行存在的限制性或级联删除外键；也不使用删除后置空导致来源 ID 丢失的关系。
- 成员目录变化或账号失效，不通过关系级联抹除分享事实。
- 分享记录长期保留，不套用媒体清理审计的 30 天保留规则，不随运行记录清理。

现有 Workflow 删除是拥有者范围内的硬删除，因此查询副本时必须同时匹配：

```text
workflows.id = workflow_shares.created_workflow_id
AND workflows.owner_uid = workflow_shares.recipient_uid
```

按查询时的真实存在性派生：

```text
copyStatus = exists | deleted
```

不新增容易与实际状态失配的持久化 `copy_exists` 或 `copy_deleted` 标记。对于正常事务创建的历史记录，目标行不存在时返回 `deleted`，前端不再把历史 ID 当作可打开地址。

存在性仅是当前查询结果，不是访问授权。查询之后又被删除的副本，打开时仍按现有权限和不存在响应处理。

### 5.3 来源名称与查询

- 新副本名称与源流程名称相同，来源不进入 `name`。
- 通过 `(recipient_uid, created_workflow_id)` 找到来源记录，再从门户成员目录获取发送者显示名。
- 列表使用分页范围内的批量查询或联表补充来源，避免每张卡片请求一次。
- 发送者不可查询时显示“来自：已不可用用户”等明确回退文案，不影响副本使用。
- 接收者重命名副本不改变来源；以后再分享该副本，新的记录指向这次的直接发送者和直接源流程，不构造不必要的多级来源链 UI。
- 自建或本人普通复制产生的流程没有分享来源时，省略来源行。

来源只随当前用户有权访问的流程返回，不开放按任意 UID 或 Workflow ID 枚举分享记录的接口，也不向接收者提供源流程访问权限。

## 6. 分享事务、并发与幂等

### 6.1 请求前检查

1. 验证登录状态、源流程归属及发送者有效性。
2. 验证版本、接收者数组、重复 UID、本人 UID、有效成员及数量上限。
3. 一次读取源名称、定义和 `revision`，与请求版本精确比较。
4. 清理并校验模板，后续所有接收者使用同一个内存中的只读快照。

源流程版本不符时在创建任何副本前返回 `409`。读取快照之后源流程又被编辑，不切换到新定义；本次仍分享已经确认并读取的旧版本快照，记录对应版本。

非法请求整体拒绝；逐成员执行时发现成员状态变化或写入失败，返回该成员的失败结果，不撤销其他成员已提交的分享。

### 6.2 每位接收者独立事务

```text
开始事务
  → 按幂等键查询已有分享记录
  → 已有记录：查询原副本当前状态并返回，不创建或覆盖
  → 没有记录：生成正常的新 Workflow ID
  → 写入接收者 Workflow，使用清理后的模板
  → 写入 workflow_shares
  → 校验目标不含媒体引用
提交事务
```

数据库唯一约束是并发幂等的最终保障。“先查询再插入”只能作为常规快速路径，不能单独保证并发安全。

若两个请求同时创建同一分享：

- 只有一个事务能够写入唯一分享记录并提交。
- 唯一键冲突的一方回滚整个事务，包括其候选副本。
- 回滚后重新读取已提交分享记录，返回该副本的当前状态。
- 不留下无来源记录的额外副本，也不产生记录存在而副本从未成功提交的状态。

`repository.CreateWorkflow` 当前自身管理事务。实现时应在仓储内组织分享事务，按需复用接受 `tx` 的写入逻辑，不能在外层分享事务中调用使用全局 DB 独立提交的创建方法。

### 6.3 重试与删除边界

- 返回响应丢失后，客户端使用相同源版本和接收者重试，数据库返回此前结果。
- 副本被接收者修改后，重复分享不覆盖它。
- 副本被接收者删除后，唯一记录仍命中，返回 `copyStatus: deleted`，不恢复或重新创建。
- 新源版本具有新的幂等键，允许创建新的副本。
- 首期不加入“同版本删除后强制重新发送”开关；如果以后需要，另行设计显式再次投递语义，不能绕过当前唯一约束。

成员处理采用有界方式，沿用项目简单直接的逐人处理模式即可，不引入队列或后台任务。请求取消或超时时回滚尚未提交事务；此前已提交的接收者结果仍通过分享记录可重查。

这是元数据操作，使用现有业务请求的有限超时及数据库上下文取消，不机械照搬 Canvas 复制媒体的长超时，也不自动重试整批创建新的业务身份。

## 7. 接口设计

以下为拟新增或扩展契约，实际响应外层沿用现有 API 封装。

### 7.1 共用成员选择

建议将中性的成员查询能力暴露为：

```http
GET /api/v1/share-recipients?search=张&page=1&pageSize=20
```

复用现有门户成员查询与权限规则。保留原 Canvas 成员查询路由作为兼容入口，共用相同实现，避免 Workflow 依赖 Canvas 专属业务接口。

### 7.2 分享 Workflow

```http
POST /api/v1/workflows/:id/share
Content-Type: application/json
```

```json
{
  "revision": 73,
  "recipientUserUids": ["member-a", "member-b"]
}
```

服务端从登录上下文取得发送者。请求不接受 `sender_uid`、目标拥有者、Graph 或媒体地址等客户端替代数据；接收者仅能来自校验通过的 UID 集合。

返回示意：

```json
{
  "deliveries": [
    {
      "recipientUserUid": "member-a",
      "status": "shared",
      "workflowId": "workflow-copy-a",
      "copyStatus": "exists",
      "message": "已分享"
    },
    {
      "recipientUserUid": "member-b",
      "status": "shared",
      "workflowId": "workflow-copy-b",
      "copyStatus": "deleted",
      "message": "此前已分享，副本已删除"
    }
  ]
}
```

契约说明：

- `status: shared` 表示该幂等键对应的分享曾成功提交；不等同于副本当前存在。
- `workflowId` 对应记录中的 `created_workflow_id`；即使删除也可以作为历史标识返回。
- `copyStatus` 只在 `shared` 结果中提供。
- `status: failed` 表示该成员本次无法完成分享，返回可展示的 `message`，不伪造副本 ID。
- 前端必须结合 `status` 和 `copyStatus` 展示结果，不能将已删除副本渲染成可访问成功链接。

错误处理沿用当前 HTTP 和错误结构：未登录、无权访问／对象不存在、非法参数、版本冲突以及系统异常分别处理；`409` 继续使用现有 Workflow 版本冲突约定。逐成员结果不泄露数据库错误、其他用户对象信息或凭据。

普通分享接口仍要求拥有可访问的源流程。源流程删除后，不通过分享接口绕过权限查询任意历史记录；接收者现存副本的来源查询继续有效。

### 7.3 列表和详情补充来源

在拥有者可见的 Workflow 列表／详情中增加可选字段，例如：

```json
{
  "shareSource": {
    "senderDisplayName": "张三",
    "sourceVersion": 73,
    "sharedAt": "2026-09-10T08:00:00Z"
  }
}
```

仅返回界面需要的来源信息。底层保留源 ID 和双方 UID 用于追踪；无需把完整记录、发送者原始素材或源定义暴露给接收者。

流程列表只展示实际存在的流程，不为已经删除的副本创建历史卡片。本期不新增独立分享历史页面。

## 9. 实施顺序

### 阶段一：清理规则与数据契约

- 确定新增表模型及唯一约束，明确禁止级联删除。
- 实现 Definition 清理与结构校验，覆盖图片、视频、混合流程及嵌套扩展参数。
- 固定接口字段、版本语义及副本已删除的返回方式。

交付条件：模板保留全部结构及提示词，媒体引用为空，源对象不被修改。

### 阶段二：分享服务与事务

- 接入成员与源流程权限校验。
- 实现每接收者原子写入、并发幂等及响应丢失后的重试。
- 实现副本状态派生和来源批量查询。

交付条件：成功记录和副本同时提交；并发重复请求不产生多余副本；删除副本后重试不恢复。

### 阶段三：前端入口与来源展示

- 流程卡片增加分享入口，共用成员选择能力。
- 展示模板范围、保存版本、提交状态和逐人成败。
- 接收卡片增加独立来源文字，保留原名与现有布局。
- 对已删除历史副本提供准确反馈。

交付条件：接收者能打开空素材模板继续编辑；Canvas 原分享流程无行为回退。

### 阶段四：联调与验收

- 使用本地测试成员及测试流程验证完整闭环。
- 完成针对性测试、类型检查、生产构建和 Chrome 交互检查。
- 整理迁移与发布说明，不自动提交或部署。

## 10. 验证与验收标准

| 范围 | 必测场景 | 预期 |
| --- | --- | --- |
| 模板结构 | 图片、视频、混合流程，多步骤引用中间输出 | 节点、端口、槽位、顺序及连线完整 |
| 提示词和配置 | 中文提示词、合法模型参数、1～9 个输出及现有上限 | 参数一致，不新增重复数量设置 |
| 媒体清理 | `mediaId`、旧地址字段、Blob、嵌套媒体／凭据字段 | 无结构化素材或凭据泄露；清理不改变源对象 |
| 结果隔离 | 有多次运行及重试结果的源流程 | 副本没有运行、结果、任务或媒体引用记录 |
| 空输入 | 未填写素材、源媒体过期或删除 | 可分享模板，实际运行仍检查缺失输入 |
| 权限 | 未登录、非拥有者、无效成员、本人、重复 UID、超限 | 按现有权限规则拒绝，不泄露对象信息 |
| 源版本 | 请求旧版本、读取快照后源流程更新 | 旧请求先冲突；已取得快照不混入新版本内容 |
| 事务 | 副本写入失败、分享记录写入失败 | 同一接收者两者全部回滚，无孤立副本 |
| 并发幂等 | 两请求同时分享相同版本给同一人 | 只有一个副本和一条分享记录 |
| 重试 | 响应丢失、部分成员成功后请求取消 | 重试复用已提交记录，不重复创建 |
| 接收者编辑 | 重命名、修改节点后再次收到同版本请求 | 名称和内容不被覆盖，来源不丢失 |
| 删除副本 | 删除后查记录、再次分享、访问旧 ID | 记录和 ID 保留，状态 deleted，不复活，旧入口不可访问 |
| 删除源流程 | 源删除后打开接收副本、查询其来源 | 副本独立可用，来源仍可追踪 |
| 新版本分享 | 同一源新 revision 分享给同一成员 | 生成新的副本与记录 |
| 来源查询 | 多卡片、发送者停用或不可查询 | 批量查询，降级文案，不扩大权限 |
| UI | 深浅主题、窄屏、卡片点击、弹窗分页与重复点击 | 风格一致，分享不误开卡片，状态清楚 |
| Canvas 回归 | 共用成员能力抽取后的原 Canvas 分享 | 原媒体复制和成员选择行为正常 |

验证手段：

- Go 针对性服务、仓储、接口测试；并发唯一约束和回滚用项目实际数据库类型的隔离测试环境验证。
- Bun 覆盖分享 API、成员选择、部分失败、来源显示及 deleted 状态处理。
- TypeScript 检查和前端生产构建。
- Chrome 使用测试成员验证“分享 → 接收库展示 → 打开 → 重命名 → 删除 → 重复分享”的闭环。
- 通过测试替身或任务调用计数确认分享不会调用生成供应商；浏览器验收不发起收费生成。

本文编写阶段不执行上述实施验收，也不将规划中的测试描述为已通过。

## 11. 数据迁移、发布与回退

- 数据变更为新增表和索引，不重写现有 Workflow、运行记录或媒体数据。
- 当前项目使用 GORM 模型注册／迁移机制；实施时按现有方式接入，发布前检查实际 DDL、唯一约束及删除行为。
- 现有普通副本没有可靠分享来源，不推测或批量补造历史分享记录。
- 上线顺序应保证数据库和后端能力先可用，再启用前端入口；不在接口尚不可用时让按钮提交。
- 分享记录体积随成功的“源版本 × 接收者”组合增长，仅存元数据；长期保留并纳入现有数据库容量与备份管理，不建立额外媒体副本。
- 功能回退时可关闭入口或回退相关代码，但保留已创建副本和分享记录。不得通过删表回退丢失幂等历史，导致再次上线时重复创建。
- 目标副本删除后继续保留分享记录，是数据契约的一部分，迁移或后续清理脚本不得破坏。

实施代码不等于获得部署授权。数据库迁移、生产发布、Docker 重建及真实成员分享操作按后续明确授权执行。
