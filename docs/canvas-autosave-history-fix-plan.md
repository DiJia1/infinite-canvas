# Canvas 自动保存漏存修复方案

日期：2026-09-10

状态：排查结论与待实施方案；本文不表示代码已经修复或上线。

排查基线：线上版本 `ab139896033b752fcd1247f94ff896b064d033ba`。本地已有未发布修改，实施时应在保留这些修改的基础上修复。

## 一、问题与修复目标

本次反馈为：用户约 13:33 退出画布应用后，再次进入，新增节点和连线没有恢复。

排查发现，服务端保存请求可以正常返回成功，但请求保存的可能仍是旧节点集合。前端显示了新内容，却没有把它们同步到负责持久化的项目 Store；之后的视角保存仍能产生新版本，因而仅查看 HTTP 200 或“已保存”不能证明当前画面全部保存。

修复目标：

1. 撤销、重做之后，新增、修改和删除节点、连线仍能正常自动保存。
2. 节点、连线、遮罩、画布设置和视角使用一致的最新文档进入现有保存链路。
3. “已保存”必须对应当前可持久化内容，不能仅表示某份旧文档保存成功。
4. 离开画布前同步尚未提交到 Store 的编辑内容，保留现有用户隔离、版本冲突和编辑租约保护。
5. 失败、生成中和未生成的图片节点不因生成状态被排除；保留现有媒体权限与有效性检查。

本轮只编写修复文档。后续修复不需要新增数据库字段、替换保存接口或重新生成图片。

## 三、已复现的前端缺陷

### 3.1 历史恢复完成条件无法成立

普通 Canvas 恢复历史快照时执行：

```ts
setNodes(entry.nodes.map(normalizeVideoConfigNodeSize));
```

历史控制器通过引用相等判断快照是否已经应用，其中包括：

```ts
left.nodes === right.nodes
```

即使每个节点都不需要尺寸归一化，`map()` 仍创建新数组。实际渲染的节点内容可以与历史快照一致，但数组引用已经不同。因此 `completeApplication()` 无法确认恢复完成，`isApplyingRef.current` 持续为 `true`。

### 3.2 节点保存被阻断，视角保存仍继续

节点同步 effect 遇到 `isApplyingRef.current` 或 `isPausedRef.current` 会直接返回，不执行 `updateProject()`。

视角同步是另一条路径，它只更新 `viewport`。Store 将新视角合并到此前的项目内容，因此仍能发送“旧节点 + 新视角”的保存请求。

```text
撤销 / 重做
    ↓
恢复时创建新的 nodes 数组
    ↓
历史恢复完成判断不通过
    ↓
新节点、节点修改和连线停留在编辑器状态
    ↓
缩放 / 平移继续把旧项目内容提交服务端
    ↓
保存回执成功，用户却无法在重新进入后恢复新内容
```

本地尚未发布的导航修改会在离开时补写视角，但仅补写视角不能解决上述节点漏存问题。

### 3.3 已完成的验证

排查阶段使用线上基线版本的历史控制器，在隔离临时目录运行 Bun 最小复现：

1. 创建基线快照，新增配置节点并记录历史。
2. 执行撤销，恢复回调通过 `map()` 设置节点。
3. 确认节点内容正确恢复，但数组引用不同。
4. 调用历史完成检查后，应用标记仍未解除。
5. 再添加生成结果节点，节点保存门禁仍被阻断。

上述断言通过，确认缺陷可复现。此验证没有写入服务器或调用生成接口；它不是完整浏览器回归，也不是修复完成证明。

## 四、失败、错误和未生成图片是否影响保存

**生成状态本身不影响保存。是否可保存，取决于文档是否合法、所引用媒体是否存在且有访问权限，以及同步链路是否正常。**

以下表格讨论图片状态带来的影响；网络中断、登录失效、版本冲突、文档超过大小限制等仍可能独立导致保存失败。

| 图片情况 | 当前保存行为 | 需要区分的边界 |
| --- | --- | --- |
| 空图片节点、尚未开始生成 | 可以保存占位节点、位置及配置 | 不要求必须先有 `mediaId` |
| 正在生成，尚无结果 | 可以保存节点及已有任务、状态信息 | 刷新后的任务恢复按现有任务机制处理，保存成功不等于生成成功 |
| 上游生成失败、任务报错，无结果图片 | 可以保存错误节点及已有错误信息 | 无须删除失败节点才能保存；若节点另带无效媒体引用，则按无效引用处理 |
| 预览加载失败、临时签名地址失效，但媒体引用合法 | 不会仅因预览失败拒绝保存 | 显示资源与持久化引用分开；保存时不逐个检查 OSS 文件能否读取 |
| `mediaId` 对应记录不存在、正在清理，或用户无权访问 | 拒绝整次文档保存 | 不会悄悄跳过该引用后保存剩余节点 |
| `mediaId` 字段格式非法，例如非字符串 | 拒绝保存 | 属于文档校验错误 |
| 本地图片上传中或上传失败，只有本地存储键、还没有 `mediaId` | 其余内容可以保存；该本地上传节点及相连连线当前会从服务端文档中排除 | 本地浏览器仍可能保留数据，但不能视为已上传到服务器，也不保证跨设备恢复 |

当前服务端遇到不可用媒体引用时返回：

> 画布引用的图片不存在、无权访问或正在删除，请刷新后重试

编辑器顶部通常显示“保存失败”；版本冲突显示“版本冲突”，离线且有待同步内容显示“离线待同步”。生成失败提示属于节点状态，与顶部保存状态是两回事。

`expires_at` 或播放/预览签名过期并不直接等价于上述不可用引用：保存校验主要检查媒体记录、清理状态和权限。不能通过前端看到裂图就推断整次保存必然失败。

本次历史恢复缺陷与图片成功或失败无关。即便所有引用合法，它仍可能阻断最新内容进入保存链路。

## 五、实施方案

### 5.1 修复历史应用完成确认

保留历史记录去重的快速比较方式，将“历史是否重复”和“本次历史应用是否完成”分开处理。

采纳本次评审建议：每次 Undo / Redo 创建递增的 `applicationId`，完成判断不再依赖 `nodes`、`connections` 或其他快照数组的引用相等。历史记录去重仍可保留现有比较方式。

`applicationId` 必须随对应编辑器快照在同一次 React 状态提交中生效，之后才发送完成确认。不能在 effect 中读取控制器“最新的 ID”并直接确认，也不能单独更新 ID 就认为节点、连线等字段已应用完毕。

三个标识各自负责不同边界，不得混用：

| 标识 | 用途 |
| --- | --- |
| 历史 `applicationId` | 识别当前等待完成的历史应用，排除旧应用回调 |
| 项目恢复代次 / 用户与项目身份 | 排除切换画布、账号或重新载入前的回调 |
| 文档同步 generation（确有需要时补充） | 识别当前待持久化内容，与服务端保存回执对应 |

具体约束：

- 节点不需要转换时避免无意义地复制数组；但不能把这一优化当作唯一修复，因为真正需要尺寸归一化时引用仍会变化。
- 确认只能结束当前那次应用，连续撤销、重做或切换项目后，旧回调不得解除新应用的状态。替换基线、重置和销毁控制器时，作废尚未完成的应用；同一有效作用域内不能重用旧 ID。
- 恢复过程中到达的生成结果、上传回调等更新使用当前状态合并。完成确认只结束历史应用，不得再次写入旧历史快照而覆盖这些更新。
- 异步结果须匹配当前账号、项目、节点及对应任务或上传操作。仍有效的结果必须保留；已删除节点、被替换任务或离开的画布不能被旧回调恢复或覆盖。
- 保留恢复期间防止重复记录历史的作用；不能只删除保存门禁而不修完成确认，也不能在调用 `setState` 后立即假定状态已经提交。
- 不使用固定延时强制清除标记，不引入全局事件总线或新的历史存储体系。

### 5.2 让最新文档进入现有 Store

在普通 Canvas 编辑页内收敛文档写入逻辑，使用最新已提交状态构造完整项目补丁，包含：

```text
nodes
connections
maskResources
backgroundMode
showImageInfo
viewport
```

普通编辑、历史恢复、交互过程中的稳定状态及视角变化，都持续更新同一个待发布完整文档。发布时取得当前作用域内最新的已提交状态，不拼接不同 render 的字段，也不从旧 Store 节点集合补齐缺失字段。

完整文档随后交给现有 `updateProject()`、文档清理和同步队列。新的变化替换尚未发布的旧文档，已有防抖负责控制频率；不另建缓存或保存接口。

关键要求：

- **历史暂停和保存暂停解耦。** `history.pause()` 只控制 Undo / Redo 历史记录的合并或暂停；`history.applying` 只用于历史应用生命周期与避免重复记录。两者都不再作为项目自动保存的布尔门禁。
- 自动保存保留自身的初始化、权限、冲突、完整快照与防抖控制。只发布一致的已提交快照；拖动结束、取消交互或失焦时可提前 flush，但持续编辑时不依赖这些事件才能保存。
- 视角更新不能在编辑器已有未发布节点变化时，只与旧 Store 文档合并。
- 继续使用现有防抖与文档去重，避免每次拖动帧都发送请求或对整个文档做深比较。
- 用户、项目 ID、恢复代次必须匹配；只读、编辑租约失效和冲突状态不得强制写入。
- 服务端规范快照恢复期间保留初始化保护，避免刚打开画布就把旧本地状态反写服务器。

### 5.3 离开页面只作 flush 保险

顶部返回、底部首页及已接入的站内离开操作共用现有导航出口：

1. 结束当前交互时，如有最后一次编辑变化，仍通过日常使用的同一个入口更新 pending document。
2. 在身份与编辑权限仍有效时，flush 已存在的最新 pending document，取消对应防抖等待，将其交给现有 Store 和本地持久化链路。没有待发布变化时不制造额外保存。
3. 沿用已有同步状态与失败处理，不把“已进入本地队列”标成“服务端已保存”。

离开入口不另行构造一套快照，不负责首次发现此前一直未跟踪的节点变化。日常编辑必须持续自动保存。浏览器关闭、崩溃或断电不保证异步网络请求完成；`pagehide` / `beforeunload` 只能作补充，不能作为唯一远程保存机会，也不能承诺强制关闭后一定完成远端保存。

若本地写入或已有保存检查失败，应保留待保存内容与明确状态，不能直接刷新服务器版本覆盖本地修改。

### 5.4 修正“已保存”的判定

沿用普通 Canvas 的紧凑状态样式，不新增常驻面板。

- 当前可持久化编辑内容尚未进入 Store，或仍在等待同步时，显示等待保存/保存中。
- 只有当前文档已获得对应同步确认，且没有新的持久化修改时，才显示已保存绿勾。
- 较早请求的成功回调不得清除较新修改的待保存状态。
- 临时 Blob 地址、资源加载状态等显示数据不应制造新的文档脏状态。
- 尚未上传到服务器的本地图片保留上传状态提示，明确其不属于已完成的云端保存范围。

当前 Store 已通过 `changedWhileSaving` 检查 dirty、pending、操作类型、标题及提交前后的文档差异，防止已进入 Store 的新修改被旧回执误清空。本次优先保留并测试这一机制，主要补足编辑器状态进入 Store 前的缺口，不能把它描述成必须从零新增的功能。

如现有状态不足以表达待发布文档，才补充本地 document generation：请求绑定自己提交的 generation，回执只能确认该版本，不能把回执到达时的最新 generation 一并标为已保存。标识绑定账号与项目，不新增数据库字段。比较对象使用现有清理后的持久化文档，避免临时 URL 更新造成永久 dirty。

### 5.5 保留媒体校验与失败节点

- 不过滤生成失败、生成中或空图片节点来规避保存错误。
- 不自动清空无效 `mediaId`，不把媒体权限校验失败改为部分成功。
- 不修改现有媒体删除、保留期和引用事务规则。
- 本地上传节点在取得 `mediaId` 后，应按既有上传完成链路进入云端文档；本次不改变其未完成时的服务端持久化协议。

## 六、影响模块与实施顺序

| 模块 | 拟调整内容 |
| --- | --- |
| `use-canvas-history.ts` 及其测试 | 历史应用完成确认、暂停与恢复的边界 |
| `canvas-client-page.tsx` | 历史接入、最新完整文档同步、视角与离开前落盘 |
| `use-canvas-store.ts` | 核对现有版本与待同步逻辑；仅在确有缺口时补充，不重写同步机制 |
| `canvas-sync-feedback.tsx` | 根据真实同步状态展示，保持现有样式 |
| 文档清理与本地上传工具及测试 | 回归失败节点保留、临时数据清理和未上传节点边界 |
| Workflow 历史接入 | 共享历史控制器的兼容性回归，不改流程调度和生成业务 |

按两个可独立评审的提交组织实施，两者完成后才验收整套修复。

### Commit 1：历史应用与保存门禁修复

- 引入历史 `applicationId` 及对应状态提交后的完成确认。
- 处理连续 Undo / Redo、基线替换、项目切换与旧确认失效。
- 解耦历史 pause/applying 和自动保存，不能把这一步推迟到 Commit 2。
- 覆盖 Undo / Redo 后新增、连接、删除、修改仍进入现有保存链路。
- 覆盖历史应用期间有效的生成结果或上传完成回调，以及失效回调不得覆盖现状态。
- 同步回归 Workflow 对共享历史控制器的使用。

Commit 1 应独立修复“历史应用卡住导致后续编辑无法保存”，但尚不能宣称完整解决视角与旧文档混合、导航 flush 等问题。

### Commit 2：完整文档发布与最新保存状态

- 收敛完整 document publish 与 pending document，视角不再单独携带旧 Store 文档保存。
- 复用 dirty/pending 和现有保存回执检查，必要时补充本地 document generation。
- 确保旧请求成功不能把新修改显示为已保存。
- 导航只 flush 同一份最新 pending document，补齐立即返回与刷新回归。

### 每个提交的验证顺序

1. 先加入对应失败测试，在本次修复前执行并确认因目标缺陷失败，保留失败原因。
2. 修复后运行相关 Bun 测试，包括真实编辑器接入与必要的 Store 竞争用例。
3. 在 `web` 下执行 `bun run typecheck` 和 `bun run build`。
4. 检查本次 diff，执行 `git diff --check`；暂存后核对 `git diff --cached --check` 与实际提交内容。
5. 上述检查通过后再创建对应提交；失败时先修复，不通过提交绕过检查。

## 七、验收要求

| 场景 | 预期结果 |
| --- | --- |
| 撤销后新增图片、配置、文本及连线 | 新内容进入保存请求，重新进入后存在 |
| 连续撤销、重做，节点数组内容相同但引用不同 | 应用状态正常结束，后续编辑仍保存 |
| 连续应用 X、Y，X 的完成确认晚于 Y 启动 | X 不得解除 Y；只有 Y 对应状态提交才能确认 Y |
| 恢复时确有节点尺寸归一化 | 既恢复规范尺寸，也不会卡住应用状态 |
| 历史应用期间收到模拟生成结果或上传完成回调 | 新结果不丢失，最终快照包含最新内容 |
| 同类异步回调到达时，节点已删除或任务已替换 | 不重新创建已删除节点，不用旧结果覆盖新任务 |
| history 持续 pause，但编辑器已有稳定修改 | 自动保存按自身防抖继续运行，不依赖 resume 才恢复保存 |
| 拖动后释放、取消或失焦 | 操作正确合并历史，最终文档仍保存 |
| 修改节点后缩放、平移并立即返回 | 最新节点、连线和视角共同保留 |
| 第一次保存未完成时又发生第二次编辑 | 第一次成功不能把第二次修改标为已保存 |
| 生成失败、生成中和未生成图片 | 合法节点正常保存，不要求先生成成功 |
| 预览失败但媒体引用合法 | 不因展示失败阻止文档保存 |
| 无权限、已删除或正在清理的媒体引用 | 保存明确失败，事务不出现部分成功 |
| 本地上传失败、尚无 `mediaId` | 保留本地上传提示；服务端排除边界与现有协议一致 |
| 切换账号、切换画布、只读、冲突及租约失效 | 旧回调不写新项目，不覆盖他人版本 |
| Workflow 使用共享历史控制器 | 撤销重做及保存不回归，不触发实际生成 |

### 必须通过的完整操作链

```text
新增节点 A
→ 等待保存完成
→ Undo（Ctrl+Z / macOS 对应快捷键）
→ Redo（Ctrl+Y / macOS 对应快捷键）
→ 新增节点 B
→ 新增 A、B 间合法连线
→ 缩放 / 平移
→ 等待“已保存”
→ 刷新页面
```

A、B 选择当前连接规则允许的节点类型，例如文本节点与生成配置节点；等待保存之外，测试须确认 A 已进入可撤销历史，避免把历史防抖时序误当成目标缺陷。刷新后必须同时核对 A、B、连线及 viewport，而非仅验证节点数量。

另以可控时序覆盖历史应用开始后、对应 React 状态提交前，以及提交后、完成确认前两类时点：注入模拟生成结果或上传完成回调。有效结果须合并到最终文档并可保存，applying 必须结束；过期 applicationId、节点和任务回调必须被正确忽略。不得通过实际收费生成构造这些时序。

## 八、已有数据恢复边界

修复代码只能防止继续漏存，不能自动找回从未进入持久化文档的坐标和连线。

恢复工作应单独处理：

1. 只读整理该账号现存成功任务、结果媒体与生成时间，逐个确认媒体实际可访问。
2. 若用户浏览器仍保留有效本地草稿或编辑器状态，先导出保全，再判断是否包含丢失节点和连线。因为本次缺陷可能发生在写入 Store 之前，不能承诺本地草稿一定完整。
3. 如只有结果媒体可用，可在另建的恢复画布中补回图片节点；原位置、连线和编辑顺序未必能恢复。
4. 不使用保存回执的版本号冒充历史文档，不自动覆盖用户目前的画布，不调用收费生成来替代丢失数据。

本方案未执行恢复写入。实际恢复到用户画布前，应展示可恢复清单和目标画布，确认具体恢复范围。
